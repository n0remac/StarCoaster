## Limits

The first browser attempt on flat `economy-e3-open` (`run-data/player-economy-e2-browser-1793983937/`) mined and built the Refinery but could not train: that layout-v1 test map has a native CHK Command Center without a corresponding authored park target `scenario:base`. The Frontier fixture contains that target and completed the production path.

The first Frontier browser run (`run-data/player-economy-e2-browser-1793985249/`) passed mining, gas and fifth-SCV observation but failed its reload assertion. On reload, the object index took 171.22 seconds, the WebSocket closed, and the browser launcher treated its stale “connecting” state as indefinite. The browser retry policy was changed to rejoin after a bounded 120 seconds in that state. The post-fix graphical rerun result is recorded below; the first run is retained as failed evidence.

The next browser run (`run-data/player-economy-e2-browser-1794007981/`) did reconnect after a 152.40-second object-index build and trained a fifth SCV, but its first gather and Refinery actions rejected with missing resource-site/catalog state. Its native host had paired all seven resources at frame 648 after the first `world.ready`; a park map-load/first-snapshot race could discard those early actions. A red-first paired-resource heartbeat regression now verifies a bounded 240-frame replay in Go, and the park's first native snapshot preserves a catalog that arrived beforehand. This run remains failed evidence; the repaired late-join path requires a new browser check.

The following run (`run-data/player-economy-e2-browser-1794009327/`) eventually accepted the two mineral gathers and Refinery build after a delayed join, but an earlier gas request had rejected before the Refinery state arrived, so its fixed-tick probe failed. A red-first plugin regression also exposed that a lost `clientReady` callback could suppress all later replay attempts. The client now retries readiness after 200 animation ticks and clears the pending flag on map change. The probe retries only explicitly rejected pre-dispatch actions with the same request ID; it does not replay an accepted or ambiguous native order. This run also remains failed evidence.

The next run (`run-data/player-economy-e2-browser-1794010258/`) accepted two mineral gathers, Return Cargo, Refinery construction and gas gather through the browser; OpenBW accepted SCV training at frame 54651 and the host published new worker `openbw:3001`. The graphical browser had not yet observed that fifth worker at its 240-second cutoff, so the harness failed before reload. The following attempt used a 15 ms native frame interval to reduce graphical client backlog and a bounded additional 180-second wait for the worker marker. The failed run remains evidence of a performance-sensitive client lag, not a browser completion pass.

The 15 ms run (`run-data/player-economy-e2-browser-1794028867/`) failed earlier: two WASM gateway sockets opened and closed with EOF after 40 seconds each, and the client never received a native snapshot. The pinned WASM `StarCoasterConnectionState` hook reported a connected socket as fully joined before OpenRCT2 authentication completed, suppressing a new join after the second EOF. Patch `0026-wasm-connection-state.patch` now requires native `Auth::ok` for the ready state. `OPENRCT2_WASM_LOCAL=1 BRIDGE_BUILD_JOBS=1 scripts/project.sh build-wasm`, the patch reverse check, and `python3 scripts/verify-wasm-bundle.py build/wasm-client` passed with one build job. The failed attempt remains startup evidence; the post-patch browser result follows.
